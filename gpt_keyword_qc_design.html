GPT Keyword QC 标注设计文档

Reranker 训练数据 · 关键词质量控制

背景

Reranker 训练需要高质量的 (query, document, label) 三元组。上游 recall 系统（BM25 + Embedding）产出的关键词候选质量参差不齐，需要对候选关键词进行质量评分，筛选出适合注入训练的正负样本。

标注流程

1
构建输入
从 pair DB 或 P1 union 读取商品-候选词对，按商品分组，附带完整产品上下文（title、brand、category、key_attributes 等）。
2
GPT 逐条评分
每次标注单位为一个商品 + 其全部候选关键词。模型在拿到完整产品上下文后，对候选词列表整体理解并逐条打分。
3
解析结果
从模型结构化输出中提取每条候选词的 final_score 及辅助字段，写入 parsed JSONL。
4
生成训练数据
按分数阈值划分正负样本，输出 training_pairs JSONL 供 reranker 训练使用。

Prompt 设计

Prompt 分为两个部分：System Prompt（角色定义与评分规则）和 User Template（每次请求的商品上下文与候选词）。两者均为独立配置文件，运行时动态加载，修改规则无需改代码。

System Prompt 原文

SYSTEM
You are labeling keyword candidates for e-commerce reranker training.

Your job is not generic semantic relevance ranking.
Your job is to assign a high-signal training score to each keyword candidate.

Use a two-track judgment process for every candidate:

1. correctness track
- decide whether the keyword is correct and safe for this product
- check product identity, brand, model, variant, size, pack count,
  and product-vs-accessory consistency

2. value track
- decide how useful the keyword would be as a top-ranked search term for this product
- a keyword can be correct but still weaker if it is too broad, too generic,
  too redundant, or not the best phrase to rank highly

The primary output is `final_score`, an integer from 0 to 3:
- `3`: core keyword, strongest label
  - captures the main product identity, key model, or most important product phrase
  - should be ranked near the top by a reranker
- `2`: correct and useful, but not the strongest
  - clearly relevant and usable
  - not the best core phrase, or slightly broader / more secondary than score 3
- `1`: weak but related
  - partially useful, broad, redundant, awkward, or lower-confidence
  - related enough to deserve a small positive signal, but rank below strong candidates
- `0`: incorrect or unsafe
  - wrong product, wrong brand, wrong model/spec, wrong accessory/main-item relation,
    or otherwise not suitable

Use strict commerce matching rules:
- reject brand conflicts
- reject obvious product-type mismatch
- reject accessory keywords when the product is the main item
  (unless the product itself is clearly an accessory)
- reject major model/spec/variant conflicts
- downgrade information-seeking keywords when they do not cleanly fit product matching
- prefer exact, specific, high-signal keywords over broad or weak keywords

Important scoring guidance:
- do not give `3` unless the keyword clearly captures the product's main identity
- a keyword can be correct but still only `2`
- a keyword can be related but still only `1`
- avoid using `3` for pure feature words, scenario words, packaging words,
  or generic category words when a stronger core phrase exists
- do not reject a keyword only because it is somewhat broad if it is still clearly
  about the same product; use `2` or `1` instead of `0`

Map to the output schema like this:
- `match_label` mainly reflects correctness
  - clearly wrong -> `reject`
  - weak / partial / lower-confidence -> `borderline`
  - clearly correct -> `keep`
- `injection_value` mainly reflects usefulness
  - weak -> `low`   decent -> `medium`   strong -> `high`
- `final_score` is the main training label

Required score consistency:
- `final_score=0`  → should normally use `match_label=reject`
- `final_score=1`  → should usually use `match_label=borderline` or a weaker `keep`
- `final_score=2`  → must be correct enough to keep
- `final_score=3`  → must be a top-quality core phrase

Scoring policy:
- use score `3` sparingly for only the clearest core phrases
- use score `2` for good usable phrases that are not the single strongest core phrase
- within the same score level, prefer more exact and product-specific keywords
- candidate rows are already ordered by an upstream system
- earlier rows can be treated as a weak hint only, never as proof of correctness or quality
- if an early row is wrong, still give it a low score
- if a later row is clearly the best match, it can still receive a high score

分段分析

第 1 段 任务重新定义

开篇第一句话做了一个关键的负向限定：「not generic semantic relevance ranking」。

这是刻意的区分。通用语义相关性打分会把「宽泛但相关」的词判为正例，但 reranker 训练需要的是高信息量的训练信号。一个宽泛词既不能帮助模型区分商品，也不应该获得高分。这一段确立了整个标注的核心目标：不是判断「相不相关」，而是判断「能不能作为优质训练信号」。

第 2 段 双轨判断框架

将打分拆解为两个独立维度，是这个 prompt 最核心的设计决策：

  • Correctness：关键词与商品是否匹配？偏向事实判断，检查品牌/型号/类目/配件关系
  • Value：即便正确，训练信号有多强？偏向价值判断，过滤宽泛、冗余、泛化的词

两条轨分开判断，避免「宽泛但正确」的词被过度奖励，也避免「精准但稀有」的词被错误惩罚。辅助字段 match_label 和 injection_value 分别对应这两条轨的输出，用于人工审核时拆解模型的判断逻辑。

第 3 段 4 级评分体系

选择 4 级而非二元（0/1）是一个重要的精度权衡：

  • 二元标注会把所有「正确」词混在一起，丢失强弱信息
  • 4 级可区分「核心词 / 可用词 / 弱词 / 错误词」，支持后续转换时灵活调整阈值

特别地，3 分门槛刻意设计得很严格——必须「captures the main product identity」，强调的是产品主体身份，而非仅仅相关性。这防止了分数通胀，确保 3 分真正代表高质量正样本。

第 4 段 电商领域硬规则

这一段是领域专属的拒绝规则，补充了模型通用能力无法覆盖的电商细节：

  • 品牌冲突：同类目竞品关键词应直接拒绝，不因「品类相同」给分
  • 配件 vs 主品：「充电器 for iPhone」和「iPhone」是不同商品，模型需显式被提示这种区分
  • 信息意图词降级：「怎么选 XX」类词不适合作为商品检索词，即便技术上「相关」

这些规则从电商 QC 经验中提炼，专门应对 recall 系统引入的典型噪声类型。

第 5 段 防止两类打分偏差

这一段处理两种方向相反的打分偏差：

  • 防止 3 分通胀：明确禁止把纯特征词、场景词、包装词打 3 分，即便它们正确
  • 防止过度拒绝：「不要因词稍宽泛就给 0，应给 2 或 1」——避免标注过激，丢失弱正样本

两条原则共同维持分数分布的合理性。过多 3 分稀释正样本质量；过多 0 分丢失训练信号多样性。

第 6 段 字段映射与跨字段一致性

明确指定三个输出字段各自代表哪个维度，并给出跨字段一致性约束（如 score=0 应对应 match_label=reject）。

设计意图是：三个字段互为校验。人工审核时可通过 match_label 和 injection_value 快速理解模型的判断逻辑。一旦出现不一致（如 score=0 但 match_label=keep），说明模型理解存在误差。

第 7 段 处理上游排序的锚定偏差

上游 recall 系统已经对候选词排过序，这个排序会干扰标注吗？Prompt 的策略是：

「earlier rows can be treated as a weak hint only, never as proof」

排序只是弱提示，不构成权威。靠前的词不一定正确，靠后的词如果更精准仍可得高分。这防止了模型对排序产生锚定偏差（anchoring bias），确保标注质量不依赖于 recall 排序的准确性。

User Template 原文

USER TEMPLATE
Product context:
- region: {region}
- product_id: {product_id}
- language_hint: {language_hint}
- brand: {brand}
- category: {category}
- title: {title}
- key_attributes: {key_attributes}
- short_description: {short_description}

Candidate keywords:
{candidate_block}

Candidate row format:
- each row is `row_id <TAB> source_code <TAB> keyword`
- `source_code` is one of:
  - `B` = both routes matched
  - `S` = sparse route only
  - `D` = dense route only
  - `U` = unknown

Label all candidates.
Then return:
- `candidate_labels`
- a short `global_notes`
设计说明 User Template 的信息组织
  • language_hint：帮助模型判断关键词的语言是否与地区一致，如 BR 地区出现泰文词应被降级
  • 候选词 TSV 编码：candidate_id 压缩为短行号（1, 2, 3...），减少 token 消耗；解析阶段再还原回原始 ID
  • source_code：B/S/D 来源路由作为弱信号附带，供模型参考，不作为打分依据
  • global_notes：要求模型对整批候选词给出整体说明，便于人工审核时快速理解模型的整体判断逻辑

打分标准

双轨判断

正确性（Correctness）

  • 该关键词是否描述的是这个商品？
  • 检查类型、品牌、型号、规格、变体、配件 vs 主品
  • 有明确冲突的直接判 reject

价值（Value）

  • 即便正确，这个词作为训练信号有多大用处？
  • 过于宽泛、通用、冗余的词价值低
  • 精确描述商品核心身份的词价值高

最终评分 final_score

3
核心关键词
精准命中商品主体，应排在最前
2
正确但非最优
相关且可用，但不是最佳核心词
1
弱相关
部分相关，过宽泛或置信度低
0
错误或不适用
品牌冲突、型号不符、配件混淆等
  • 3 分需严格把控，只给最清晰的核心词
  • 一个词可以是正确的，但仍只值 2 分
  • 一个词可以是相关的，但仍只值 1 分
  • 不因词稍宽泛就直接给 0，应给 2 或 1

辅助字段

final_score 是最终使用的训练标签，辅助字段用于人工审核和错误分析。

字段维度取值
match_label正确性keep / borderline / reject
injection_value价值high / medium / low
reject_reason拒绝原因10 类枚举，见下节
short_reason说明模型的简短文字解释

标注例子

以下为真实标注案例。商品为巴西市场的卡车 LED 大灯套件，候选词来自 BM25 + Embedding 双路 recall。

BR Farol Led Olho Anjo Com Suportes Cargo 2428 1722 2426 1519 Branco
Category Spare Parts → Lighting → LED Headlights Description KIT 04 FAROIS OLHO DE ANJO PARA FORD CARGO BIVOLT · 适配 Ford Cargo 1519 / 1719 / 1933 / 2428 / 2429 等型号
#来源关键词ScoreMatchValue拒绝原因模型说明
1B farol de led olho de anjo 3 keep high — 核心词，精准描述产品主体（LED angel eyes 大灯）
2D farol led angel eyes 2 keep medium — 英文同义词，正确但语言混用，稍弱于葡语核心词
3B farol ford cargo 2428 3 keep high — 精准型号匹配，主要兼容车型，强核心词
4B lâmpada H4 plug&play 0 reject low wrong_product H4 灯泡（散件），非卡车大灯套件
5B farol moto led angel eyes 0 reject low wrong_product 摩托车大灯，商品为卡车，车型不符
6B farol ford cargo 2 keep high — 覆盖多个 Cargo 型号，正确但不如精确型号（2428）强
7S farol de milha angel eyes 0 reject low wrong_product farol de milha = 雾灯/辅助灯，商品为主大灯
8S farol led 7 polegadas 0 reject low spec_conflict 指定 7 英寸尺寸，商品无此规格，存在冲突

同样是 angel eyes 相关词：葡语核心词（#1）得 3 分；英文同义词（#2）得 2 分；摩托车版本（#5）和雾灯版本（#7）词面相似但商品类型不符，直接得 0 分。型号精确词（#3）和泛型号词（#6）均为正确，但精确词得 3 分，泛型号得 2 分。

执行方式

两种模式输出格式完全一致，解析逻辑可复用，可按场景互换使用。

大批量 · 生产

Batch 模式

提交后异步等待结果，适合大规模生产标注。支持 submit / poll / download / parse 四个子命令。

小批量 · 调试

Sync 模式

并发实时调用 API，适合小批量测试和快速验证 prompt 效果。
