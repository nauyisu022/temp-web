Search Tree DAG Design

source: SEARCH_TREE_DAG_DESIGN.md updated: 2026-04-15 16:56 UTC

1. 目标

当前这套搜索词结构，核心目标已经从“做一棵树”改成“先存真实关系图，再按需要投影成树或局部图”。

原因很简单：搜索词之间天然存在多归属关系。
例如：

  • 磁吸行動電源推薦 同时属于 磁吸行動電源 和 行動電源推薦
  • 犀牛盾手機殼 同时属于 手機殼 和 犀牛盾
  • 汪汪隊玩具 同时属于 汪汪隊 和 玩具

如果一开始就强行压成单父树，很多真实关系会被抹掉。

因此当前设计采用：

  • 底层结构：DAG（有向无环图）
  • 展示结构：局部树图或局部关系图

2. 当前结构

2.1 节点

每个搜索词是一个节点。

节点当前至少包含：

  • term：归一化后的词面
  • impressions：聚合曝光
  • clicks：聚合点击，当前只在部分流程里保留

2.2 边

边表示“父词更泛，子词更具体”。

当前边方向统一为：

parent -> child

例如：

行動電源 -> 小米行動電源 -> 小米行動電源20000

2.3 图类型

当前默认语义已经改成：

  • max_parents=0：父节点不限制，保留全部通过筛选的父边
  • max_parents=1：输出单父树投影
  • max_parents>1：输出受限多父图

因此“真实结构”应该理解成 DAG，树只是它的一个投影。

3. 建图流程

3.1 词面归一

按地区做不同归一规则：

  • TW：去空格，保留连续字形
  • BR/ID/MY/PH/SG/VN：保留空格，压缩多空格

这一步的目标是让词面比较稳定，减少因为空格、大小写、兼容字符造成的重复节点。

3.2 候选父词召回

按语系分开：

CJK（中文）

使用连续字串候选。

例如：

藍牙耳機推薦

会产生：

  • 藍牙耳機
  • 耳機推薦
  • 藍牙
  • 耳機
  • 推薦

Latin（葡语等）

先按空格切词，再取连续短语。

例如：

fone bluetooth jbl

会产生：

  • fone bluetooth
  • bluetooth jbl
  • fone
  • bluetooth
  • jbl

这里的目标是避免拉丁语系退化成任意字符切片。

3.3 父词筛选

候选父词还要经过约束：

  • 父词必须在词库里存在
  • 父词曝光要高于子词
  • 父词不能高到离谱
  • 过短、纯数字、弱词要过滤

3.4 打分与保留

当前打分主要看：

  • 候选长度
  • 父子曝光比例
  • 是否前缀
  • 是否后缀

在拉丁语系里：

  • 多词短语优先于单词父词
  • 前缀短语优先于中间短语

最后：

  • choose_parent_term() 返回一个主父词
  • choose_parent_terms() 返回多个父词
  • build_tree_index() 生成单父树索引
  • build_graph_index() 生成多父图索引

4. 当前导出物

4.1 局部树图页面

用于快速看某个根词下面的结构。

当前脚本：

  • scripts/render_search_tree.py

可输出：

  • 单父版本
  • 多父受限版本
  • 多父不限制版本

4.2 GitHub Pages 发布钩子

当前脚本：

  • scripts/publish_search_tree_reports.py

当前站点目录：

  • search_tree_reports/index.html
  • search_tree_reports/tw/index.html
  • search_tree_reports/tw/*.html

4.3 台湾全量浏览器

为了避免“一个根词一页”把静态站撑爆，当前已经改成：

  • search_tree_reports/tw/graph.json
  • search_tree_reports/tw/explorer.html

这里的 graph.json 是台湾全量 DAG 数据，explorer.html 在浏览器里动态渲染局部图。

这一步是当前设计的关键变化：

不是“全量预渲染为几万张 html”，
而是“全量图数据 + 一个浏览器页面”。

5. 为什么要这样设计

5.1 搜索词天然不是树

一个词同时属于多个更泛词，本来就是常态。

如果只保留单父节点：

  • 结构更好画
  • 但信息会丢失

如果底层保留全部父边：

  • 更接近真实搜索意图
  • 后续分析更稳定
  • 展示时仍然可以随时投影成树

5.2 GitHub Pages 不适合全量静态页面

如果台湾 54k+ 个根词都单独导出 html：

  • 文件数太多
  • 总体积太大
  • 发布、浏览、维护都会变差

因此全量图更适合：

  • 一个 json
  • 一个 explorer.html

5.3 层次分离更清楚

当前结构可以分成三层：

第一层：原始图

全量 DAG

第二层：展示投影

从 DAG 中截某个根词的局部子图

第三层：具体页面

  • 单父树图
  • 多父局部图
  • 全量浏览器

这样每一层职责都比较明确。

6. 现在这个结构可以怎么用

6.1 查某个泛词下面都长出了什么长尾词

例如：

  • 行動電源
  • 收納
  • 手機殼

适合做：

  • 词库巡检
  • 类目词扩展
  • 长尾发现

6.2 查一个词的多归属关系

例如：

  • 汪汪隊玩具
  • 犀牛盾手機殼
  • 磁吸行動電源推薦

适合做：

  • 判断词应该挂在哪些上位词下面
  • 发现“品牌 + 品类”双归属
  • 发现“属性 + 需求词”双归属

6.3 做召回词扩展

如果线上有一个查询词：

  • 可以向下取子词，做更具体的扩展
  • 也可以向上取父词，做泛化兜底

例如：

小米行動電源

可以扩到：

  • 子词：小米行動電源20000
  • 父词：行動電源

6.4 做关键词推荐

对于运营、标注、词库整理，当前结构适合给出：

  • 同父兄弟词
  • 父词
  • 子词
  • 多父词

这比只给“相似词列表”更容易解释。

6.5 做词库清洗

当前图里会暴露三类问题：

  • 意图词混入产品词
  • 品牌词和品类词混挂
  • 一词多义导致的大类污染

例如：

  • 茶碗蒸 -> 茶碗蒸做法
  • 康乃馨 同时挂出花、尿布、手套

这些都可以用来反推：

  • 黑名单词
  • 需要拆分的节点
  • 需要补约束的边规则

6.6 做训练或评估特征

未来可以把图结构作为额外特征：

  • 父词数量
  • 子词数量
  • 根词深度
  • 所属大类
  • 是否多父词

这对：

  • 查询理解
  • 排序特征
  • 生成质量评估

都可以有帮助。

7. 当前局限

7.1 台湾规则仍以字串包含为主

中文这边现在还是连续字串召回，所以会带来：

  • 意图词挂接
  • 非严格短语边
  • 同形异义混挂

7.2 多父不代表全都合理

max_parents=0 的含义是“保留全部通过当前筛选的父边”，
不是“这些父边都百分之百正确”。

所以多父图现在更适合作为：

  • 分析工具
  • 巡检工具

还不适合作为完全可信的线上结构。

7.3 根节点定义仍然来自当前规则

如果某个词没有父边，它就会成为根节点。
但这不一定代表它真的是语义上的最高层，只代表当前规则没有把它挂上去。

8. 下一步更值得做的事情

8.1 台湾全量浏览器再补两个交互

  • 根词搜索联想
  • 节点点击后切换为新根词

这样浏览效率会高很多。

8.2 在局部图里区分“主父边”和“附加父边”

当前所有边画法接近。
后面可以做成：

  • 主父边：实线
  • 附加父边：虚线

这样更容易读。

8.3 增加兄弟词面板

当前页面只画图。
后面可以增加：

  • 当前词的父词列表
  • 子词列表
  • 同父兄弟列表

这会比纯图更实用。

8.4 巴西按同样方式补全量浏览器

巴西已经更接近短语结构。
在拉丁语系里，DAG 的可解释性通常会更强，比较适合下一步接上。

9. 一句话概括

当前这套设计，本质上是：

把搜索词组织成一个全量 DAG，再按场景投影成树图、局部图和静态浏览目录。
